# Planned for 0.10.0 — pipes and `>` to a file

**Status:** planned, not built. Saved from the planning session so it can be picked up later.
Nothing in this document is implemented in the current release.

---

## Scope, deliberately small

Two things, and no new infrastructure:

1. **`|` pipes any command's output into the next command.**
2. **`>` writes the final output to a file** (and `write <file>` is the explicit form).

No workspaces, no folder picker, no native host, no new manifest permissions, no settings UI, no
extra backends. The file lands wherever the browser puts downloads, with the name you give.

## How the file write works (the whole mechanism)

The overlay is ordinary DOM in the page, so it can do what any "save this" button does:

```js
const url = URL.createObjectURL(new Blob([text], { type: 'text/plain' }));
const link = document.createElement('a');
link.href = url;
link.download = name;
link.click();                       // the browser saves it, no permission needed
URL.revokeObjectURL(url);           // a tick later
```

That is a real file save to the user's Downloads folder (subject to the browser's own download
settings), with zero permissions, zero background messages and zero install.

**Honest limits:**

- Browsers strip path separators from `download=`, so `>` writes **flat file names** —
  `> windows.txt`, not `> out/windows.txt`.
- The browser's download settings apply, including "ask where to save" if the user has it on.
- Writing the same name twice makes the browser pick `windows (1).txt`; that is browser behaviour,
  not something BMUX can override.

The write sits behind a single `writeTextFile(name, text)` helper, so a later release can add
folders or real directories without touching the pipeline layer.

## The rule

**Every command's output is pipeable and redirectable by default.**

- `list-windows > windows.txt`, `help > help.txt`, `help | write help.txt`, `keys | head -n 5`,
  `info state > state.txt`, `capture-pane > text.txt`, `eval document.title > title.txt`,
  `filter links -q | write links.txt`.
- No command opts in, and any command added later gets it for free: the dispatcher already returns
  one value per command, `|` passes it on, `>` writes it.
- **Consumers are opt-in.** Only the small text toolkit reads `api.stdin`; everything else ignores
  it and still produces redirectable output. `filter` is the most interesting producer, not a
  requirement.

## Value model

```
value := string | { text, items? }        // items: [{ url?, text? }]
```

- `>` writes `text`.
- If `text` is empty and `items` exist, it writes the items' `url`/`text`, one per line.
- If both are empty, it writes an empty file and logs "no output".
- `|` hands the whole value on; `api.stdin` is always present at the head of a pipeline.

## Syntax

Top level only (outside quotes and `[] () {}`), exactly like `;` today:

| Written | Means |
|---|---|
| `a \| b` | run `a`, feed its value to `b` |
| `a > file.txt` | run `a`, write its value to `file.txt` |
| `\;` `\|` `\>` | literal characters |
| `>>`, `\|\|`, `&&` | **refused** with a short message (not implemented, not guessed) |

Semantics worth stating:

- A failing stage ends **that pipeline** with its error; the `;` chain carries on.
- Prompts pause a pipeline — use `-y` (`filter links -y`).
- `sleep` between stages works and paces a demo.
- `>` after a `;` segment applies to that segment only.

```
list-windows > windows.txt
help | write help.txt
keys | head -n 5
list-panes | grep %2 | wc -l > counts.txt
filter links -q | write links.txt
```

## Commands (+7 → 77)

| Command | Reads stdin | Does |
|---|---|---|
| `write <file> [-]` | any | save the pipeline's value to `<file>`; `-` prints instead of saving |
| `grep <pattern> [-v]` | text | lines matching (case-insensitive) |
| `head [-n N]` / `tail [-n N]` | text | first/last lines (default 10) |
| `sort [-r]` / `uniq` | text | over lines |
| `wc [-l]` | text | lines / words / chars |
| `filter … -q` (flag) | — | collect matches without drawing, for the next stage |

That is the minimum that makes pipes useful without turning this into a shell.

## Tests to write

**jsdom**

- Parser: `|`, `>`, escaped `\| \> \;`, pipes inside quotes/brackets, `>>`/`||` refused, empty
  stages, trailing `>`, redirect with no pipeline, `;` plus pipes.
- Runner: ordering, stdin threading, a stage returning `{ text, items }`, a failing stage aborting
  only its pipeline, `sleep` between stages, prompts pausing, `-` (print) mode.
- Toolkit: `grep/sort/uniq/head/tail/wc` on known input; `filter -q` items; `write` receives the
  right name and text through a stubbed `writeTextFile`.
- **Universality, generated from the registry**: for all existing commands, run `cmd > out.txt`
  and assert the redirect layer handled the result — one call to `writeTextFile`, no redirect
  error, empty only where the command prints nothing.
- Regression: the existing suite stays green.

**Chromium**

- `Page.setDownloadBehavior` to a temp dir; `list-windows > windows.txt`, `keys | head -n 5`,
  `info state > state.txt` and `filter links -q | write links.txt` each produce the file on disk
  with the expected content.

## Explicitly not in this release

`>>` append, folders, workspace selection, File System Access, `download` for images, the native
terminal bridge. Each is a separate decision later, and none of them is blocked by this plan:
`>` goes through `writeTextFile()`, and the pipeline layer only knows "a value came out".
